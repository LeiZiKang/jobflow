# 推进求职：每个岗位都有下一步

入口：`00-工作流系统/推进求职.html`。它与 brief、业务视图一样从状态生成，不能手改。

## 日常推进顺序

1. 按 START_HERE 冷启动，领取单主租约。设置 `JOBFLOW_SESSION_REF` 为自己领取租约时的 session-ref；不能借用其他活跃会话的租约。
2. `jobflow.py sync-progress --actor <自己>`：幂等同步岗位准备、草稿审核、跟进与检索运行检查；不会授权发送，不会把任务直接记成完成。
3. `jobflow.py next`：先处理已有机会的只读状态检查，再准备已批准岗位。各岗位独立推进，不等待同批全部决定。
4. 按任务 ID 生成 executor 信封。浏览器全部使用 ego lite；遇登录、验证码、控制权丢失立即停，并把可复核原因写到任务中。
5. 任务结束必须留下结果文件、状态和下一步。只有写了报告却未入账不算完成闭环。

## 已批准岗位的准备

- 岗位范围已批准，不反复问用户是否投同一岗位。
- 核实候选档案中的同一个 JD URL、平台岗位 ID、公司和岗位；岗位失效或目标发生变化就停止，不自行找替代岗位。
- 核对打招呼语的事实和用词。已有草稿不等于已批准；不要把 RxSwift 与 RAC 说成同一套东西，不从“使用过”推成“熟练”。
- 输出精确发送文字、实际附件版本及 JD 回读证据。调用 `prepare-candidate` 建立 application 和单独的最终审批任务。
- 最终审批任务绑定该 application、平台和外部动作；附件与文字用精确文件摘要绑定。
- 同时按 `runbooks/电话准备.md` 准备岗位专属来电脚本，登记到application.phone_prep；投递后缺脚本必须补，不以旧通用面试材料替代。工作台“我的简历”只展示私人材料registry里明确登记的现有版本。

## 草稿审核与入池

- `sync-progress` 把每日 candidates JSON 登记到 `state/progress.json`。按平台岗位 ID 与现有 candidate/application 去重；已有投递只关联，不重复创建。
- 审核待处理草稿：核实 JD 时效，按用户 `goals.json` 的偏好排序；所有制未知就标未知。旧草稿不自动当成有效岗位。
- 保留原始草稿；审核结果通过 `review-draft --draft-id ... --disposition promoted|rejected|stale --note ... --evidence-ref ... --actor ...` 记录。
- promoted 还需要 `--dossier <审核完成的HTML岗位档案>`；新 candidate 初始必为 awaiting_user，不会自动批准或投递。
- 每个草稿只处理一次；重复岗位自动关联现有记录。中途失败可以重复 sync，不新增重复任务。

## 跟进

- 到期任务是只读核实，不是自动发催促。先读取平台当前状态；没有新回复就记录“截至某时未见回复”，不能推断拒绝。
- 记录 source_ref、observed_at、next_check_due；没有取得平台页面时记 blocked，不写成零回复。
- 使用 `record-followup` 完成这次检查并创建下一次检查；关闭案件不会继续生成跟进任务。
- 已完成或已取消的跟进不再按旧日期触发；已经关闭的案件保留历史，不恢复主动联系。

## 最终审批与证据 v2

1. 使用 `request-approval` 的 `--application-id --operation --platform --content-file/--payload` 创建具体发送包的审批请求。仅有自由文本 scope 的历史审批不能授权新的外部操作。
2. 用户对具体目标、文字和附件批准后，记录 `decide-approval`。用户决定的来源必须真实，不得自行批准。
3. 在外部操作之前执行 `claim-approval`，传入同一 application、task、operation、platform 和 payload 文件列表。目标、内容、有效期、任务依赖不一致时拒绝；领取一次后不能再次领取。
4. 执行后保存平台截图与回读，再用 `evidence-record` 记账。新证据自动消费本次领取，不需要再手动消费。没有成功证据就停留未验证，不能重试发送来补账。
5. 应用进入 submitted_verified 必须有与该 application 匹配的 application_submit + verified_success + audit pass 证据。失败或其他操作的截图不能替代提交成功。

历史 manifest 与审批原文由 `state/evidence_policy.json` 冻结引用，缺口明确保留。冻结历史不等于补批，也不允许复用；`evidence-verify --strict` 仍可指出历史未消费/自审问题。

## 写入与恢复

核心 CLI 的 mutation 使用同一仓库级文件锁；活跃租约期间核对 session-ref。正常异常会回滚业务状态、审批和事件，不留下半个 CLI 操作。
这是协作写入约束，不是操作系统权限隔离：直接编辑 JSON 的程序仍可能绕过它。进程被强杀/断电的跨文件恢复未承诺自动完成；重新接管必须 validate，有矛盾先停外部动作。

完成后运行 `scripts/check-all.sh`；只提交当前任务改动。用户原有未提交内容不能一起扫入提交。
