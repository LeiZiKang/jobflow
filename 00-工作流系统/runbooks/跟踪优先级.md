# On trace 关注优先级

规则：先看已投聊天，对长期没有回复的岗位降低优先级。该规则只改变投入排序，不自动关闭岗位，也不减少每日平台核实。

| 等级 | 条件 | 处理 |
|---|---|---|
| P1 先处理 | 明确轮到用户回复、交材料、确认或准备面试 | 优先处理具体下一步；发送仍须单独批准 |
| P2 正常跟进 | 等对方不足 7 个自然日，或对方约定的回复日期尚未到 | 保持正常关注 |
| P3 降低关注 | 等对方 7–13 个自然日 | 减少主动投入，先推进其他机会 |
| P4 低优先 | 等对方至少 14 个自然日 | 保留每天只读核实，不反复催问；有实质回复再升级 |
| 待核实 | 未看清聊天窗口、登录受阻或无法确认轮到谁 | 不把未知当成无回复，不据此降级 |

7/14 天是工作排序经验阈值（置信度中），不是录用概率或雇主拒绝的判断。平台已读/送达、推广提示、系统推荐、我方追加消息，都不是招聘方回复。

## 等待起点

从最近一次招聘方实质回复之后，第一条尚未获答复的我方消息开始算。没有任何招聘方回复时，从首次发送算。自己追加催问不重置起点；对方真实回复后重新判断轮到谁行动。

如果对方明确约定回复日期，使用 expected_reply_date 延后降级计时。日期、行动和约定必须有聊天证据；不能猜测最后回复时间。遇到仅 App 可读的消息，保留未核实范围，不把它当成空消息。

## 数据与命令

applications.engagement 保存实际聊天结构，attention_priority 保存本次计算结果；UI 和核实顺序使用它排序。

```json
{
  "observed_at": "实际观察时间（带时区）",
  "waiting_on": "employer",
  "waiting_since": "本轮首次未获回复消息的日期",
  "last_outbound_date": "最近我方消息日期",
  "last_inbound_date": null,
  "response_window_verified": true,
  "action_needed": null,
  "platform_contact_label": "已核实的联系人及平台公司名",
  "source_refs": ["实际聊天回读和截图路径"]
}
```

用 `jobflow.py record-chat-priority --application-id ... --snapshot-file ... --actor ...` 保存。只在当前窗口已核实后填写 response_window_verified=true。

每日 On trace 结果的每条 observation 可以带 engagement（不重复 observed_at/source_refs），批量记账会同步优先级。已有明确“等对方”的岗位，新的 no_reply/unread 观察会沿用原起点重算；blocked 保留上次等级并标出受阻；发现回复则先失效旧等待判断，必须重新确认当前行动方，不能沿旧时钟继续降级。

所有低优先级仍纳入 10:00 核实；排序不授权消息发送、附件上传、撤回或关档。
