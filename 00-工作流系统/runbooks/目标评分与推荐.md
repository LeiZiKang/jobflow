# 目标偏差评分与推荐

author: codex · 2026-09-22 · v1待用实际反馈校准

目标来自仓库外 `JOBFLOW_PROFILE_DIR/goals.json`（默认 `~/.config/jobflow/profile/goals.json`）。身份资料放同目录独立的 identity.json，检索/评分只读 goals，不把姓名、电话、邮箱注入查询。

## 决策顺序

1. 保留来源、观察时间及当前招聘状态。JD未完整核实、已投、明确拒绝过或已关闭的岗位不能自动推作新机会。
2. 硬线独立评估 pass / fail / unknown。已证实触犯用户确认的地点、工时、团队或用工硬线等，不得用薪资加分抵消。未知不冒充通过。
3. 计算目标匹配的证据支持分与未知可能上限，同时展示证据覆盖率。分数不是录用概率；不得为凑排名臆造事实。
4. “真外企”仅在境内主体到外资母公司的控制关系有来源且核实后赋予。境外上市/投资方名单/港澳台独资标签不足以单独证明。未核实标“所有制待核实”。另标自研产品/外包·交付/用工性质待核实。
5. 先按推荐 / 待核实 / 不推荐分组。仅当 goals 的 `foreign_first=true` 时，在同组内优先已核实外企，再比较最低匹配分、证据覆盖率与候选 ID。false、null 或缺省都不按所有制分层；null/缺省表示未定，评分照常可用。用户未回答时写 null，不替用户选 true/false。所有制偏好不能越过硬线或证据门槛。
6. 推送分为“推荐投递”“值得先核实/聊”“不推荐”；硬线未知的只能进待核实。没有达到推荐门槛的就明确写本轮没有，不强行补足数量。每天最多优先展示5个，其他保留报告。

## 初始权重（工程默认，未冒充用户逐项定权）

模板维度是技术与经验30、工时与生活25、成长环境20、薪资匹配15、文化与休假10；合计100，须由用户确认或调整。地点与明确硬线单独判断。阈值、权重与偏好从外置goals读取，版本随每次评分保存。某项技术“用过”不能升级“熟练”，大型App参与不能自动视为架构主导。

## 证据与解释

每一维写 observed_at、source/evidence_refs、事实、推断、未知和偏离原因。招聘方宣传、平台标签、集团文化不可直接认定具体团队WLB良好。冲突来源并列并降为待核实。旧调查必须标日期，不以当日评分时间替代核实时间。

股权至少写：招聘展示主体、已知/未知合同主体、直接股东与比例、控制链、最终母公司、证据链接及日期、断点。无法打开要标“未查询/登录受阻/付费限制/工具受阻/公开信息不足”中的真实原因，不能只写未核实。

## 推荐与操作分离

评分不得改用户批准/拒绝状态，也不得自动投递、发消息、上传简历或接受声明。已批准岗位可以准备可审阅发送包；具体对外动作仍需批准。

## 本地执行

研究者按 `00-工作流系统/examples/screening/assessment.example.json` 写带证据的assessment（不用虚构样例的事实）。先运行 `python3 00-工作流系统/bin/jobflow_screening.py <assessment.json>` 检查，Decider复核后在自己租约下执行 `python3 00-工作流系统/bin/screeningctl.py --input <assessment.json> --actor <agent>`。该命令保存state/screening.json、追加事件并刷新岗位目录；工作台显示分数和tags。不会改变投递/审批状态。报告展示实际计算的goal_config_sha256，输入和输出都要留档。更新个人goals后需重新评审和生成报告，旧报告的hash保留，不假称已重算。
