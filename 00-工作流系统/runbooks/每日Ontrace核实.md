# 每日 On trace 平台进度核实

每天按 `state/recurring_jobs.json` 的排期（建议排在岗位检索之后），对每个 On trace 岗位到相关投递平台更新进度。这里只读核实，不发催促、消息或再次投递。

## 开始

1. 只从仓库冷启动；领取自己的 Decider 租约并设置 JOBFLOW_SESSION_REF。其他租约有效时不抢占，记录阻塞。
2. 运行 `jobflow.py scheduled-bootstrap --job job-daily-ontrace-check --scheduled-for <当日排期时间的带时区ISO>`；NO-OP 则停止。
3. 用 `python3 00-工作流系统/bin/ontrace_check.py targets` 读取当轮全部目标，保存到本轮证据目录。范围动态取已提交且未关闭、拒绝或撤回的记录；新投递下轮纳入，已结束的移出。submitted_unverified 明确标为待确认，不能当成已验证投递。
4. 按平台合并浏览，但逐岗位核对。BOSS、猎聘使用相应聊天/投递记录，ATS 使用已有申请记录。平台岗位 ID、公司和岗位必须匹配，不能用搜索结果代替申请进度。

## 浏览与证据

先读 `跟踪优先级.md`。targets 输出包含联系人别名和上次 engagement：例如小站在 BOSS 联系人列表以元锦文化/郎女士显示，应对照岗位标题与聊天头部确认，不把搜不到品牌名当成没回复。按关注优先级核实，仍必须覆盖全部目标。

- 全部浏览器操作使用 ego-browser 技能和同一个任务空间。仅复用登录态，不读取 Cookie、密码、token 或验证码。
- 登录、验证码：立即停止该平台，给受影响的每个岗位记 blocked 和具体原因。其他能正常访问的平台可继续。
- 用户接管浏览器：立即停止整个浏览器操作，未完成目标逐一记 blocked，不换空间抢控制权。
- 每个岗位都记录结果：unread / no_reply / replied / blocked、实际观察时间、来源文件和简短说明。replied 可包含招聘方回复、面试通知或明确拒绝，但保留原文证据；状态迁移另按现有 Case/应用规则办理。
- 成功观察必须保留可复核页面截图或导出的回读。无变化也是一次真实观察；旧记录、打不开、未找到会话都不能写成“没有回复”。
- 只能在 App 查看的消息（猎聘「不支持此消息查看，请登录猎聘APP查看消息内容」）：必须回读完整聊天记录，按气泡位置 / 头像确认发送方，不能凭列表头部或单条预览判成招聘方回复。确认是我方发的就按无回复处理；仍判不出就记 blocked，写明需用户在 App 核实。（曾经出现过把我方自己发的 App-only 消息误判成招聘方回复的事故。）
- 工时、合同性质或团队信息发生变化，单列给用户决定；不自行撤回或关闭机会。

## 记账

把结果写到 `00-工作流系统/evidence/ontrace-<日期>/result.json`：

```json
{
  "scheduled_for": "2026-09-14T10:00:00+08:00",
  "observations": [
    {
      "application_id": "实际目标ID",
      "outcome": "no_reply",
      "observed_at": "实际观察的带时区时间",
      "source_ref": "仓库内截图或回读文件路径",
      "note": "实际观察到的内容；受阻则写原因"
    }
  ]
}
```

用 `ontrace_check.py record --result <文件> --actor <自己>` 统一写入。该命令要求所有当前目标各一条记录，拒绝遗漏、重复、虚假时间和同一天重复记账；成功更新平台核实时间，受阻只记尝试，不覆盖旧平台进度。下一次检查为次日。

先完成批量观察记账，再依据已核实通知办理应用状态迁移，避免先关闭岗位而丢掉本轮核实记录。已成功记账的结果文件不覆盖，后续补充另存带时间的文件。

如果发生实质回复或发现当前行动方不同，每条 observation 应补 engagement，包含 waiting_on、waiting_since（本轮首次未获答复日期）、last_outbound_date、last_inbound_date、response_window_verified、action_needed，按 `跟踪优先级.md` 的结构填写；observed_at 和 source_refs 由批量命令绑定。不得把平台促销、系统消息或“已读”当成招聘方回复。仅确认仍无回复时，可沿用既有起点，由程序自动更新等级。

最后运行 check-all，释放租约。不要批量提交用户已有的未提交改动。

## 通知

没有实质变化时保持安静，UI 更新核实时间即可。仅在新回复/面试通知/状态实质变化，或者新出现且需要用户处理的登录、验证码、权限问题时通知。相同阻塞未变不要天天重复提醒。向招聘方发消息仍需要具体内容的单独批准。
